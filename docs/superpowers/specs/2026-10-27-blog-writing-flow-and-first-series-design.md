## 1. 의도와 이유

이 블로그는 그 자체가 목적이 아니다. 사용자는 「AI로 무언가를 만들고 시도하고, 수익을 내며 사업을 시작해 가는 과정」을 콘텐츠로 남겨 서사를 쌓고, 그 서사로 홍보까지 하려 한다. 채널은 넷이고 역할이 나뉜다.

| 채널 | 역할 | 비고 |
|---|---|---|
| 유튜브 | 영상 | 인스타·스레드와 한 묶음 |
| 인스타그램 | 인스타툰 | 〃 |
| 스레드 | 과정을 가볍게 글로 | 〃 |
| github.io(이 저장소) | 깊은 탐구 글 | 위 묶음을 포함할 수 있으나 반드시 같이 가지는 않는다 |

블로그 글의 주제는 그 과정의 깊은 탐구와 소프트웨어 엔지니어링 심화다. 같은 주제라면 스레드에 가볍게 쌓이다가 깊은 글이 되고, 다른 주제면 따로 간다(잠정, 미확정).

github.io는 나중에 포트폴리오·프로젝트·소개가 있는 개인 홈페이지로 확장한다. 그 논의는 별도다. 다만 **「블로그는 사이트의 한 구역」이라는 전제로 지금 주소 구조를 잡는다**(사용자 동의 2026-10-27). 다른 채널이 github.io로 링크로 모이는지는 확장 때 다시 정한다.

이 문서가 다루는 것은 둘이다.

- A. 글 한 편이 초안에서 게시까지 가는 흐름
- B. 첫 시리즈 「허브·현장 체계」의 구성

## 2. 목표 · 비목표 · 반목표

**목표**
- 초안을 공개 저장소에 노출하지 않고, 사용자가 로컬 실제 화면(localhost:3000)으로 검토한다.
- 게시는 PR → CI 초록 → 사용자 「게시」 → 허브 병합 → Pages 배포 순서로만 나간다.
- 첫 시리즈 1편을 이 흐름으로 게시한다. 2편 이후는 1편 뒤 조정한다.

**비목표**
- 개인 홈페이지 확장, 댓글(Giscus)·방문 분석(GA4), E2E 테스트(첫 글 뒤 별도 이슈), 다른 채널 자동화, 글 작성 UI.

**반목표(이렇게 되면 실패)**
- AI 티가 나는 글: 근거 없는 일반론, 틀에 박힌 소제목, 겪지 않은 이야기.
- 볼트의 민감정보(토큰·키·개인 계정·고객 정보·내부 경로)가 글이나 발췌에 섞여 나가는 것.
- 게시한 글의 주소가 바뀌는 것.
- 작업 트리에 둔 초안이 다른 세션의 커밋에 휩쓸려 공개되는 것(볼트 원장에 같은 유형의 사고 기록 있음).

## 3. 제약

- **저장소 규칙(`CLAUDE.md`)**: 슬러그는 하위 폴더와 무관하게 파일명. frontmatter 필수 `title`·`description`(150자 이내)·`date`(`"YYYY-MM-DD"` 문자열)·`tags`, 선택 `series`·`seriesOrder`·`coverImage`·`draft`. GitHub Flow, main 직접 푸시 금지, main 푸시는 곧 배포. 병합 게이트 `npm ci && lint && type-check && test:run && build:production`. 단위 테스트는 `__tests__/fixtures/posts`만 읽는다(`POSTS_DIR`), 실제 글이 테스트를 깨뜨리면 안 된다.
- 로컬 게이트는 CI와 같은 **Node 24**로 돌린다(로컬 기본은 26, 볼트 memory `로컬-node24-게이트`).
- **볼트 규칙**: 사본을 두지 않는다, 심링크만. 민감정보는 볼트에도 두지 않는다.
- 공개 저장소다. 브랜치도 공개다.
- 지금 코드에서 `draft: true`는 개발 모드에서도 글을 숨긴다(`lib/mdx.ts` `_getAllPosts(includeDrafts=false)`, 호출부 전부 기본값). 걸러내는 곳은 `_getAllPosts`뿐이라 `getPostBySlug`·`getPostPaths`는 draft를 거르지 않는다. 즉 지금은 `posts/`에 `draft: true` 글이 있으면 목록에는 없어도 `/posts/<slug>/` 정적 페이지는 만들어진다.
- vitest는 `NODE_ENV=test`로 돈다. `__tests__/lib/mdx.test.ts`는 `getAllPosts()` 기본 호출에서 draft가 0건임을 단정한다(픽스처 `draft-post.mdx`).
- `scripts/generate-rss.mjs`는 로더와 별개로 파일을 직접 읽고 `data.draft`만 거른다. sitemap은 next-sitemap이 `out/`에서 만든다.
- 게시된 글이 아직 0건이다(`content/`가 비어 있고 CI는 이 상태로 `build:production`을 통과한다).

## 5. A. 글 흐름 설계

### 5-1. 폴더와 로딩

```
볼트(private)  projects/blog/drafts/<slug>.mdx          ← 초안 정본(git 추적, 비공개 저장소)
               projects/blog/drafts/<slug>/…            ← 그 글의 이미지(있으면)
저장소(public) content/drafts  -> 볼트 drafts/ 심링크    ← .gitignore
               public/images/drafts -> 볼트 drafts/ 심링크 ← .gitignore (이미지 미리보기용, 허브 결정)
               content/posts/<연도>/<slug>.mdx          ← 게시된 글
               public/images/posts/<slug>/…             ← 게시된 이미지
```

- 로더 변경(`lib/mdx.ts`), 허브가 정한 규칙:
  - **초안이 보이는 조건은 `NODE_ENV === 'development'`(= `npm run dev`) 또는 명시 플래그(예 `INCLUDE_DRAFTS=1`)뿐이다.** 「운영이 아니면」으로 잡지 않는다. vitest(`NODE_ENV=test`)에서는 기존 기본 동작이 그대로라 `getAllPosts()` 기본 호출을 단정하는 기존 테스트를 고치지 않는다. 변수 이름은 빌더 몫.
  - 그 조건이 참이면 `content/drafts/`(환경 변수로 바꿀 수 있게, `POSTS_DIR`과 같은 방식)도 글 목록에 넣고 `draft: true`도 보여 준다.
  - **운영 빌드는 `content/drafts/`를 읽지 않고, `draft: true`는 목록뿐 아니라 `getPostPaths`·`generateStaticParams`에서도 제외한다.** 그래야 「posts/에 초안이 잘못 들어가도 운영에서 안 보인다」가 직접 주소까지 성립한다. 초안 파일은 drafts에 있는 동안 `draft: true`를 달아 둔다.
  - `getPostBySlug`는 그대로 둔다(개발 모드 미리보기가 이 함수로 초안을 연다).
- 심링크는 로컬에서 한 번 만들고 저장소에는 들어가지 않는다. 만드는 절차는 README에 적는다. CI에는 심링크가 없다.
- 테스트: 픽스처 방식 그대로(픽스처 디렉터리를 읽는 구조는 바꾸지 않는다. 테스트를 **더하는** 것은 이 문서가 막지 않는다). 새 테스트는 명시 플래그와 초안 디렉터리 변수로 「개발이면 포함, 운영이면 목록·정적 경로 둘 다 제외」를 고정한다.
- **RSS·sitemap 검증**: `generate-rss.mjs`가 `content/posts`만 읽는지 확인하고, 로더 이슈 안에서 **심링크에 임시 초안을 둔 채 `build:production`을 돌려 `out/`·`sitemap.xml`·`rss.xml`에 초안이 없음을 확인**한다(임시 초안은 커밋 전에 지운다). 로컬 게이트는 심링크가 살아 있는 환경에서 돌기 때문에 이 확인이 필요하다.
- 슬러그 충돌: **posts/ 대 drafts/ 충돌만** 개발 모드에서 눈에 띄는 오류로 낸다(조용히 덮지 않는다). posts/끼리의 기존 중복 처리(`console.warn`, 첫 일치 사용)는 손대지 않는다. 운영 빌드는 drafts/를 읽지 않으므로 해당 없음.
- **이미지**: 1편은 이미지 없이 표·코드 블록으로 쓴다(허브 결정). 따라서 이미지 심링크(`public/images/drafts`)와 게시 때 경로 치환은 **이번 범위에서 뺀다.** 이미지가 필요한 편이 나오면 그때 같은 방식(볼트 폴더 + gitignore 심링크)으로 더한다. 위 폴더 그림의 이미지 두 줄은 그때의 자리다.

### 5-2. 한 편의 생애

1. **고르기**: 허브가 시리즈 구성(§7)에서 한 편을 고르고, 볼트에서 쓸 자료 경로 목록을 만든다.
2. **초안**: 허브가 부하(서브에이전트, 뼈대를 만드는 일이라 opus)에게 브리프를 준다. 브리프에는 독자·분량·자료 경로·금지 사항(§2 반목표·§5-4 점검 항목)을 적는다. 결과는 볼트 `projects/blog/drafts/<slug>.mdx`. 허브가 볼트 원본과 **문장 단위로 사실을 대조**한 뒤 사용자에게 알린다.
3. **검토**: 허브가 `npm run dev`를 띄운다. 사용자는 `http://localhost:3000/posts/<slug>/`에서 실제 화면으로 읽고, 고칠 점을 대화로 준다. 허브가 고치면 저장 즉시 반영된다. 끝날 때까지 반복.
4. **게시 결정**: 사용자가 「게시」라고 말한다. 그 전에는 아무것도 저장소에 들어가지 않는다.
5. **게시**: 허브(현장이 떠 있으면 그 현장)가 main에서 브랜치 `post/<slug>`를 만든다. 파일을 `content/posts/<연도>/<slug>.mdx`로 옮기고 `draft`를 지운다. (이미지가 있는 편이면 `public/images/posts/<slug>/`로 옮기고 경로를 바꾼다. 1편은 해당 없음.) 커밋 `feat(post): <한글 제목>` → PR(본문에 볼트 결정 링크 없음, 공개 저장소) → CI `test` 초록 → **병합 직전에 `date`를 그날로 맞춘다**(PR이 며칠 묵어도 게시일 = 병합일) → 허브 병합 → deploy 워크플로 성공 확인.
   - 정본의 이동: 「게시」 뒤 PR 브랜치에 들어간 순간부터 저장소 파일이 정본이고 볼트 파일은 이동 중인 옛 자리다. 배포 확인(6)까지 둘 다 있는 것은 사본이 아니라 이동 중 상태로 본다.
6. **배포 확인**: 라이브 `https://joonangler.github.io/posts/<slug>/` 200, `sitemap.xml`·`rss.xml`에 포함, 시리즈 내비 표시. 그 뒤 볼트 drafts의 파일을 지우고 README 진행 절에 링크와 날짜를 남긴다(사본 금지).
7. 다른 채널로 옮기는 일은 이 문서 밖이다.

### 5-3. 역할

| 단계 | 누가 |
|---|---|
| 자료 고르기·브리프·사실 대조·dev 서버·게시 PR·병합·배포 확인 | 허브 |
| 초안 쓰기 | 부하(opus) |
| 검토·고칠 점·「게시」 | 사용자 |
| 로더 변경·테스트·README 절차 | 현장(브리프 하나 = 이슈 하나) |

### 5-3-1. 순서 — 이슈 둘, 로더가 먼저

| 순서 | 이슈 | 내용 | 완료 조건 |
|---|---|---|---|
| A | 로더·초안 미리보기 | `.gitignore`에 `/content/drafts/` · 로더 변경(§5-1) · 단위 테스트 · README의 심링크 절차 · **임시 초안으로 `dev`에서 보이고 `build:production`의 `out/`·sitemap·rss에 없음을 확인**(임시 초안은 지우고 커밋) · 글 0건 상태에서도 빌드가 통과함 | PR 병합, CI 초록 |
| B | 1편 게시 | §5-2 1~6 | 라이브에 보임 |

A가 main에 있어야 B의 초안을 dev로 볼 수 있다. 하나의 PR로 묶지 않는다(로더 변경과 글은 되돌리는 단위가 다르다).

### 5-4. 게시 전 점검(허브, 게시 PR 전에 전부 통과)

- 사실: 글의 숫자·날짜·인용은 볼트 원본이나 저장소 커밋에서 확인된 것만. 확인 못 한 문장은 지운다.
- 민감정보: 토큰·키·이메일·고객명·개인 계정 식별자·볼트 절대 경로·비공개 저장소 내부 URL이 본문·코드 발췌·이미지에 없다. grep과 눈으로 둘 다.
- 형식: `description` 150자 이내, 슬러그 영문 소문자와 하이픈만, `tags` 비어 있지 않음, `series`·`seriesOrder` 시리즈 전 편과 일치, 링크 전부 200.
- 코드 발췌: 볼트 `harness/`는 비공개다. 발췌는 동작을 설명할 최소 조각만, 개인 경로는 일반화한다.
- 로컬 게이트 Node 24 rc 0.

## 6. 주소와 이름 규칙

- 글: `/posts/<slug>/`, 슬러그는 영문 소문자·숫자·하이픈. 예 `/posts/one-hub-many-fields/`.
- 파일: `content/posts/<게시 연도>/<slug>.mdx`.
- 시리즈 주소 `/series/<series-slug>/`는 시리즈 이름에서 코드가 만든다(`seriesToSlug`). 시리즈 표시 이름은 한글이어도 되나, 그러면 시리즈 주소가 퍼센트 인코딩된다. 영문 시리즈 이름을 쓸지는 §7 시리즈 이름과 함께 사용자가 정한다.
- 홈 `/`는 지금 글 목록이다. 홈페이지 확장 때 홈만 바뀌고 `/posts/`·`/series/`·`/tags/`·`/search/`는 그대로 둔다.

## 7. B. 첫 시리즈 「허브·현장 체계」

**독자**: 혼자 일하면서 AI 에이전트로 실제 작업을 돌려 보려는 개발자·1인 사업자.
**톤**: 겪은 것 중심. 구조를 왜 그렇게 잡았는지, 어디서 깨졌는지, 숫자와 실패를 그대로. 일반론과 도구 홍보는 쓰지 않는다.
**재료**: 볼트 `context/protocol.md`·`harness/skills/hub-routines`·`wiki/harness/`(하네스·승격-원장·브리프-모델-effort-기준·도구-함정)·`wiki/self/retro/`·`log.md`. 전부 비공개 원본이므로 §5-4 발췌 규칙을 따른다.

## 8. 빌더에게 맡기는 것

- 로더 변경의 구현 방식(환경 변수 이름, 함수 분리), 단위 테스트 케이스의 수와 모양, 슬러그 충돌 오류를 내는 방법.
- 심링크 생성·확인 절차의 README 문구.
- 게시 절차는 초기엔 체크리스트(§5-2·§5-4)로 둔다. 스크립트화는 두 번째 글 뒤에 판단.
- 1편의 실제 소제목·발췌·분량.

## 8-1. 검토자 질문에 허브가 정한 것(2026-10-27, 사용자가 뒤집을 수 있음)

1. 초안 노출 조건은 `NODE_ENV === 'development'` 또는 명시 플래그. 기존 기본 동작과 테스트는 그대로(§5-1).
2. 운영 빌드는 `draft: true`를 정적 경로에서도 제외한다 — 안전망이 직접 주소까지 미치게(§5-1).
3. RSS·sitemap은 로더 이슈 안에서 임시 초안으로 실측 확인한다(§5-1, §5-3-1).
4. 이슈는 둘로 나누고 로더가 먼저 병합된다(§5-3-1).
5. 1편은 이미지 없이. 이미지 심링크는 이번 범위 밖(§5-1).
6. 슬러그 충돌 처리는 posts 대 drafts만(§5-1).
7. `date`는 병합 직전에 맞춘다. 볼트 → 저장소는 이동이지 사본이 아니다(§5-2 5).
